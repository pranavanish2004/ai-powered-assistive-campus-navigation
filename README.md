# AI Campus Navigation Assistant for Visually Impaired Students

**Pilot campus:** IIT Hyderabad
**Status:** Phase 1.1 (regenerated) + Phase 1.2 complete — awaiting sign-off before Phase 1.3

## What this is

A multimodal navigation assistant intended to help visually impaired
students move around campus independently. It fuses speech, computer
vision, GPS, and a knowledge base through a rule-based Decision Engine, and
uses a multimodal LLM (MLLM) **only** for natural-language reasoning and
conversation — never for routing, localization, or perception directly.

**This assistant is a supplement to, not a replacement for, a user's cane,
guide dog, or orientation & mobility training.** It is pilot software; do
not rely on it as a sole means of hazard detection.

## Architecture at a glance

See [`docs/architecture.md`](docs/architecture.md) for full diagrams,
module dependencies, testing strategy, and a running list of risks and
future work. The two decisions to understand before touching this code:

> Safety-critical alerts (obstacle warnings, off-route drift) and
> conversational responses ("what's for lunch?") travel through **separate
> output lanes** with different latency guarantees. Safety alerts never
> wait on an LLM call. See `interfaces/text_to_speech_interface.py` and
> `navigation/engine/safety_engine.py`.

> Navigation safety state is an explicit, exhaustively-testable finite
> state machine (`navigation/engine/state_machine.py`) — not an ad-hoc set
> of conditionals scattered through the engine.

## Quick start

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"          # editable install + dev tooling
cp .env.example .env             # adjust values as needed

pytest                            # 243 tests, no PYTHONPATH needed
```

Run the API locally:

```bash
uvicorn campus_nav.api.main:create_app --factory --reload
# then, e.g.:
curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/graph
```

Interactive API docs are auto-generated by FastAPI at `/docs` once the
server is running.

Optional extras:

```bash
pip install -e ".[speech]"       # Whisper + sounddevice (heavy; not needed for 1.1/1.2)
```

## Why the package layout changed from the first draft

The original Phase 1.1 used a flat layout with `PYTHONPATH=src` set
manually for tests. That worked, but had three real problems, all fixed
now:

1. **No editable install.** `pip install -e .` is how any collaborator (or
   CI runner) should get the package on their path — not an env var they
   have to remember to export every session.
2. **No packaging metadata.** There was no `pyproject.toml` declaring
   dependencies, so "what does this project actually need to run" lived
   only in a loose `requirements.txt` with no version constraints checked
   against a target Python version.
3. **openai-whisper as a hard dependency.** It pulls in `torch` and
   `numba`, neither of which Phase 1.1 or Phase 1.2 code touches. It's now
   an optional `[speech]` extra, installed only when the speech module is
   actually being worked on.

### Phase 1.4b at a glance — Dashboard Integration

Before writing any code, the actual open-source [IITH Dashboard backend](https://github.com/LambdaIITH/Dashboard)
was read directly (not assumed from its marketing page). Findings that
shaped this design:

- Only three endpoints are genuinely public, unauthenticated: bus schedule
  (`/transport/`), city bus schedule (`/transport/cityBus`), and the
  current week's mess menu (`/mess_menu/`). Everything else (timetable,
  cab-sharing, lost & found, marketplace) requires a real `@iith.ac.in`
  Google-authenticated session this assistant cannot obtain on a user's
  behalf, and is intentionally **not** implemented.
- **The Dashboard has no campus wayfinding data whatsoever** — no
  buildings, departments, library, medical centre, faculty offices, or
  accessibility information. It's a student-life utility app, not a
  campus directory. This confirms, concretely, why the Campus Graph and
  RAG/local knowledge base (not the Dashboard) must remain the sole
  source of truth for "where is X" — a design decision made before this
  research, now verified rather than assumed.
- It's a no-SLA, community-maintained side project with no rate limiting
  implemented — treated accordingly (short timeouts, silent graceful
  degradation, never blocking navigation/vision/safety).

| Component | Default (always available) | Real backend |
|---|---|---|
| Dashboard | `MockDashboardRepository` (`dashboard_backend=mock`) | `IITHDashboardRepository` (`dashboard_backend=iith_live`) |

New endpoints: `GET /dashboard/status`, `GET /dashboard/bus-schedule`,
`GET /dashboard/city-bus-schedule`, `GET /dashboard/mess-menu` — all
return HTTP 200 even when data is unavailable (`available: false` in the
body), since that's expected, routine state for this data source, not an
application error. See `docs/architecture.md` §18 for the full research
findings and integration design.

### Phase 1.3 at a glance

Every vision component has a heavyweight-ML-free default so the app boots
and is fully testable without the optional `[vision]` extra installed:

| Component | Default (always available) | Real backend (optional `[vision]` extra) |
|---|---|---|
| Object detection | `MockObjectDetector` | `YOLOv8Detector` (ultralytics) |
| OCR | `MockOCRService` | `EasyOCRService` (easyocr) |
| Depth estimation | `HeuristicDepthEstimator` (bbox-size heuristic) | `MiDaSDepthEstimator` (torch.hub) |
| Object tracking | `IOUTracker` (pure Python, always real) | — |
| Landmark detection | `NullLandmarkDetector` (placeholder — Phase 2 per spec) | — |
| Camera source | `OpenCVCamera` (USB) | `IPCameraSource` (DroidCam/IP Webcam), `VideoFileCamera` |

Switch backends via `Settings` (`detector_backend`, `ocr_backend`,
`depth_backend`, `camera_source_type`) — no code changes needed. New
endpoints: `POST /vision/start`, `POST /vision/stop`, `GET /vision/status`,
`GET /vision/camera/status`, `GET /vision/detections`,
`GET /vision/obstacles`, `GET /vision/diagnostics`.

Obstacle detection feeds the existing Phase 1.2 `SafetyEngine` through one
new, purely additive method (`evaluate_obstacles`) — `evaluate()` and
every other Phase 1.2 API is unchanged. See `docs/architecture.md` §11 for
the full integration design.
